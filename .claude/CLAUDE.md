## Core Principles

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:

- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:

- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:

- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:

- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:

```text
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

## Source References — No Line Numbers

**Never reference code by line number in committed material.** This applies to:

- Source-code comments and docstrings (C#, Go, C++, Python, JS, etc.).
- Markdown prose in documentation and any committed `.md`.
- Markdown source-code link text — do **not** write `[file.go:42](...)`.
- Markdown source-code link anchors — do **not** append `#L42` to a clickable file path.

Refer to the target by **symbol name** — function, method, error sentinel, struct field, branch identifier, doc section heading. When the surrounding paragraph needs to point at a specific spot, name the symbol in prose and link to the file without an anchor. If a true deep link is unavoidable, use a **GitHub permalink at an immutable commit SHA** — never a `main`-branch URL with `#L<n>`.

**Why:** Every code change shifts line numbers. Comments and anchors pinned to `main` go stale on the next commit, triggering static-analyzer drift reports. Symbol names survive refactors that move code around.

**Scope:** Applies to material authored from now on. Existing `#L<n>` anchors are not retroactively removed.

## Architecture Overview

Kombine is a self-contained build system that uses Roslyn to compile and execute C# scripts. The codebase has four main layers:

### 1. **Entry Point & Configuration** (`src/`)

- `kombine.cs` — Main entry point (`KombineMain.Main()`); parses CLI args, routes to built-in actions (khelp, kversion, kcache) or script execution
- `version.cs` — Version constants
- `core/core.config.cs` — Parses `-k` parameters (-ksdbg, -ksrb, -kfile, -ko:*); initializes global state
- `core/core.constants.cs` — Exit codes, magic strings, defaults
- `core/core.state.cs` — Serialization of compiled script state (uses BinaryPack); caching logic

### 2. **Execution Engine** (`src/exec/`)

The execution pipeline compiles C# scripts with Roslyn and executes them as .NET assemblies:

- `core.exec.script.cs` — Main script compilation & execution; loads and calls action functions; handles the global code → action flow
- `core.exec.script.sourceresolver.cs` — Resolves `#load` directives (searches current dir, script dir, forward/backward paths, tool dir; supports HTTP URLs)
- `core.exec.script.assemblyresolver.cs` — Resolves `#r` directives for assemblies (ref assembly, Roslyn, BinaryPack, etc.); prevents duplicate loads
- `core.exec.tool.cs` — `Tool` class; launches external processes with queuing, parallel execution limits, output capture, environment variable inheritance
- `core.exec.tool.io.cs` — Process I/O handling; stdout/stderr capture; handles child process lifecycle

### 3. **Caching Layer** (`src/cache/`)

- `core.cache.cs` — Transparent script caching; stores compiled assemblies to disk (home folder, app data path). Detects stale cache via file hash. Supports `mkb kcache` commands.

### 4. **Public API** (`src/api/`)

The API is statically available to scripts via `using static Kltv.Kombine.Api.Statics`:

- **Types**: `kmb.value.cs` (KValue), `kmb.list.cs` (KList) — Wrapper types with operator overloads for string manipulation
- **Methods**:
  - `kmb.http.cs` — `Http.DownloadFile()`
  - `kmb.compress.tar.cs` — `Compress.Zip`, `Compress.Tar` (uses SharpCompress)
  - `kmb.args.cs` — Argument parsing
- **Built-in Classes** (in Statics):
  - `Msg` — Console output with colors, indentation, log levels (Debug/Verbose/Normal/Silent)
  - `Folders`, `Files` — Cross-platform file/folder operations
  - `Host` — Platform detection (IsWindows, IsMacOS, IsLinux, etc.)
  - `Share` — Inter-script object sharing (Set/Get), registry (Register/Registry)
  - `Exec()` — Simple synchronous execution shorthand
  - `Kombine()` — Execute child Kombine scripts

### 5. **Utilities** (`src/util/`)

- `util.extensions.cs` — Helper methods on standard types (string, etc.)
- `util.fs.internal.cs` — Internal file system utilities

## Cross-Platform Design Principles

**Path handling:** Use `Folders` API methods instead of hardcoded `/` or `\`. Paths in scripts should be relative.

**Process spawning:** `Tool` class abstracts platform differences; always use it instead of direct `Process` calls.

**File existence/permissions:** Use `Files` and `Host` APIs to detect platform quirks (e.g., `Host.IsRoot()` on Unix, special folder paths on Windows).

**Environment variables:** Export via `Export()` or `Share.Set()`, import via `Import()`. Child processes inherit the parent's environment.

**Relative imports:** `#load "path/to/script.csx"` searches in order: current dir, script dir, forward paths, backward paths, tool dir. Absolute paths bypass search.

## Release & Publishing

**Local publish script** (`kombine.csx`):

- `mkb publish` — Builds all platform packages (Windows, Linux, macOS) and creates compressed artifacts
- `mkb release` — Tags and pushes release to GitHub (using `github.csx` extension)

**CI Workflows:**

- `pr-tests.yml` — Runs on PR/non-main push; builds debug and runs test suite
- `main-release.yml` — Runs on main push; builds release, verifies single-file artifact, computes release tag (Release-x.x.YYYYMMDD), publishes to GitHub releases

**Exit codes:** As of recent changes, explicitly preserve action return values; failures default to 1, Ctrl+C is 130. See main-release.yml and README for details.

## Common Development Patterns

**Adding a new API function:**

1. Create or edit a file in `src/api/` (e.g., `kmb.newfeature.cs`)
2. Make it part of `Statics` class or create a new static class in the API namespace
3. Add `using static Kltv.Kombine.Api.NewFeature;` to the reference assembly includes
4. Test via an example in `examples/`

**Extending the tool CLI:**

1. Add parameter parsing to `core.config.cs` (if `-k` prefixed, or in `Config.ParseBuiltinAction`)
2. Add action handling to `kombine.cs` (`Main()` method)
3. Document in README.md and keep exit codes consistent

**Debugging scripts:**

- Pass `-ksdbg` flag to embed debug info
- Use VSCode with the .NET debugger; see README for launch.json example
- For Roslyn issues, enable `-ko:d` (debug output) to see compilation details

**Cross-platform testing:**

- Test path handling with forward/backward slashes
- Verify `Host` API checks work on all platforms
- Ensure `Tool` class handles shell quoting correctly on Windows/Unix

## Important Notes

- **No .NET required for end users** — Releases are self-contained, single-file binaries
- **Script caching is transparent** — First run compiles, subsequent runs use cached assembly (unless `-ksrb` flag)
- **Roslyn compilation is slow** — This is expected; cache mitigates it
- **Extension pattern** — Use `#load` for reusable .csx modules; see `extensions/` folder for examples (git.csx, github.csx, clang.csx)
- **Error messages matter** — Users get frustrated with cryptic build errors; prioritize clarity in Msg output
